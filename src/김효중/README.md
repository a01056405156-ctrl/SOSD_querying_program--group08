# SOSD 검색 성능 공통 측정 프로젝트

Visual Studio 2022 / Windows 10 이상 / C++17 / x64 / 단일 스레드.

## 중요한 측정 기준

본 프로그램은 서로 다른 성격의 **두 가지 빌드 시간**을 분리해서 기록합니다.

1. **컴파일 빌드 시간**: Visual Studio에서 `빌드 → 솔루션 다시 빌드`를 눌렀을 때 출력되는 `경과 시간 ...` 값. 프로그램 자신은 컴파일 완료에 걸린 시간을 알 수 없으므로, **사용자가 초 단위로 입력**합니다. Enter를 누르면 이 값은 생략됩니다. 모든 팀원은 `Release | x64`에서 **다시 빌드**를 사용하세요. 일반 `빌드`는 최신 상태이면 작업을 건너뛸 수 있습니다.
2. **데이터 준비 및 인덱스 구축 시간**: 사용자가 데이터셋 전체 경로를 입력하고 Enter를 누른 직후(파일 열기 **직전**)부터, 파일 열기/형식 확인/데이터 접근 준비/검색용 인덱스 생성 완료 직후까지. 이 구간은 C++ 코드의 `build_start`~`build_end` 타이머가 자동 측정합니다. 사용자가 경로를 타이핑하는 시간은 제외됩니다.
3. **실제 검색 시간**: `index.find(key, method)` 실행 전후만 측정합니다. 키보드 입력·출력 시간은 제외됩니다. 히트/미스 검색 시간을 각각 합산해 비교할 수 있습니다.

**과제 기본 지표** = 데이터 준비 및 인덱스 구축 시간(한 번) + 존재하는 키 검색 시간 합계 + 없는 키 검색 시간 합계.

**추가 요청 지표** = Visual Studio 컴파일 빌드 시간(한 번) + 위의 과제 기본 지표.

> 주의: 원본 과제의 '빌드 시간'이 일반적으로 의미하는 것은 실행 중 자료구조 구축 시간이며, **컴파일 시간은 과제 본래 채점 지표에 포함된다고 단정할 수 없습니다.** 추가 요청 지표는 팀의 별도 비교 지표로 표시합니다. 컴파일 시간은 PC·컴파일러·프로젝트 상태에 크게 좌우되므로 다른 PC끼리 비교하면 공정하지 않습니다.

시간 단위는 **나노초(ns)**입니다. 1초 = 1,000,000,000ns.

## 실행 방법

1. 저장소를 GitHub에서 클론하거나 ZIP으로 내려받아 압축을 풉니다. 원본 파일 구조를 유지하세요.
2. 공식 SOSD 데이터 파일(`uniform_dense_200M_uint32`, `uniform_sparse_200M_uint32`)을 별도로 준비합니다. 원본 데이터 파일은 각각 약 800MB이며 GitHub에 업로드하지 않습니다.
3. `SOSD_Search.sln`을 더블클릭합니다. 별도 콘솔 앱을 만들 필요는 없습니다.
4. Visual Studio에서 `Release | x64`를 선택하고 `빌드 → 솔루션 다시 빌드`를 선택합니다.
5. 출력 창의 **총 경과 시간(초)**을 확인합니다. 시간이 없다면 Enter로 생략할 수 있습니다.
6. `Ctrl + F5`로 실행합니다. 먼저 컴파일 시간(초)을 입력하고, 이어서 데이터셋의 **전체 경로**를 입력합니다. 예: `C:\SOSD_Data\uniform_sparse_200M_uint32`.
7. 검색할 `uint32` 키(0~4294967295)를 입력합니다. `q`를 누르면 다른 데이터셋 경로로 돌아갑니다.

프로그램은 `uniform_dense` 이름의 공식 Dense 데이터에는 산술 위치 계산을, Sparse/기타 정렬 uint32에는 샘플 인덱스 + 하이브리드 탐색을 사용합니다. Dense 파일은 공식 2억 개 규약(42부터 연속된 정수)을 전제로 합니다.

## 출력 항목

- `데이터 준비 및 인덱스 구축 시간`: 경로 입력 이후 파일을 열고 검색 준비를 마칠 때까지
- `이번 키 검색 시간`: 키 1회 검색
- `[과제 기준] 데이터 준비 + 이번 키 검색`: 준비 비용 + 키 1회 검색
- `누적 N회 검색 시간`: 현재 데이터셋에서 입력한 모든 키 검색 시간 합계
- `[과제 기준] 데이터 준비 + 누적 검색`: 준비 시간은 한 번만 추가
- `[확장 지표] 컴파일 + 데이터 준비 + 누적 검색`: 사용자 입력 Visual Studio 컴파일 시간까지 한 번 추가

## 공정한 실험을 위한 권장 사항

- 4명 모두 동일한 PC 및 `Release | x64`, 동일 데이터셋 파일, 동일 히트·미스 쿼리, 동일 검색 횟수, 동일 측정 구간을 사용하세요.
- 컴파일 시간은 코드를 수정하지 않고 **다시 빌드**한 결과를 별도로 기록하되 본래 과제 지표와 구별하세요.
- 파일 매핑/디스크 캐시, 초기 파일 페이지 접근 여부에 따라 결과가 달라질 수 있습니다. 순서를 교차하고 여러 번 측정하여 중앙값을 비교하세요.
- 측정 결과를 ns로 표시하더라도 실제 시계 해상도가 1ns라는 의미는 아닙니다.
- Windows Job Object는 **private committed memory**를 제한하지만 파일 매핑된 물리 페이지의 working set 전체를 512MiB 이하로 보장하지 않습니다. 과제의 메모리 판정 방식은 별도 검증이 필요합니다.
- 이 프로그램은 기존 업로드 소스코드의 탐색 알고리즘을 유지하면서 **측정 범위만 변경**한 버전입니다. 다른 팀원 코드도 같은 타이머 경계로 수정해야 합니다.
